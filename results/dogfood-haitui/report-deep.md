### DEEP-ISSUE-001：首单奖励明细成交状态筛选"条件已传后端但结果未过滤"（根因深挖）

| 字段 | 值 |
|------|-----|
| 严重级别 | medium（数据正确性） |
| 分类 | functional |
| URL | /retail/first-order-rewards |
| 接口 | POST /ops/user/retail/first-order-rewards/paging |
| 证据 | HAR 抓包 |

**描述**

上轮报告（CSV SDJLMX-006）发现"成交状态选已成交后列表仍混杂未成交"，当时只能判断"筛选疑似不生效"。本轮用 HAR 抓包深挖了根因：

选择「成交状态 = 已成交」并点筛选后，抓到的列表接口请求体为：
```
POST /ops/user/retail/first-order-rewards/paging
{"status":1,"pageNo":1,"pageSize":20}
```

即**成交状态条件已作为 `status:1` 正确传给了后端接口**（不是前端没传参）。但返回列表仍混有未成交记录（上轮多次验证）。因此缺陷精确定位为：**筛选参数已到达后端，但后端未按 status 过滤，或 `status:1` 的取值与后端期望语义不一致**——属于后端过滤逻辑/前后端取值契约问题，而非前端渲染问题。

**建议**：开发结合 paging 接口定义确认：(1) status 字段是否对应成交状态；(2) 已成交应传的值；(3) 后端是否对 status 做了过滤。奖励金状态筛选（SDJLMX-007）现象相同，一并排查。

**复现**

1. 进入 首单奖励明细
2. 成交状态下拉选"已成交"→筛选
3. HAR 抓包见请求体 `{"status":1,...}`，但列表仍含未成交行（见上轮 screenshots/sdjlmx-006-deal-done.png）

**备注**：HAR 录制存在时序不稳（偶发 0/1 requests），本结论基于成功抓到的那次请求体；status 字段语义为依据参数名与上下文的推断，建议以接口定义为准。
