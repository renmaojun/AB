### 4-补. 品牌/型号搜索联想框 — 已打通（第二轮，关键突破）

经用户澄清：品牌/型号是"搜索联想选择框"——不输入任何字符点击不出结果，必须输入字符触发搜索，再从下拉选。据此第二轮找到了可行的自动化路径：

1. **定位真实输入节点**：`eval` 查 DOM 发现品牌/型号的可输入元素是 `input.ant-select-input`（之前 `@eN` 命中的是外层包装，故输入无效）。页面从上到下的 `input.ant-select-input` 依次为 后台类目/品牌/型号/商品类型。
2. **触发搜索**：`eval` 聚焦目标 input（`document.querySelectorAll('input.ant-select-input')[n].focus()`）+ `keyboard type "<关键词>"` → 成功触发联想搜索，下拉弹出候选。
3. **精确选择**：`eval` 在下拉中点击文本匹配的 `.ant-select-item-option` → 选中成功。

实测结果：
- 品牌：输入"H"→联想出 ceshipinpai / Hisense / TOSHIBA → 选中 "Hisense" 成功。
  - 附带发现：输入中文"海信"→"暂无数据"，输入"H"→命中"Hisense"。品牌联想按英文名/拼音匹配，中文名"海信"在品牌库中不存在（可记录为数据/体验问题）。
- 型号：品牌选定后，型号框输入"A"→联想出型号候选（1PLA03PDCN0D、ASDFGG、BCD-190F/A 等）→ 选中 "ASDFGG" 成功。
- 商品名称/编码：标准 `ant-input`，`find placeholder ... fill` 成功填入。

**结论**：品牌/型号这类"输入触发搜索 + 下拉选择"的联想框，agent-browser **可以驱动**，但需配合 `eval` 做两件事：(a) 聚焦到内部真实 input（而非外层包装）；(b) 在选择时限定在"当前打开的下拉浮层"内取选项，否则会误选到其他 ant-select 的残留选项。

证据：screenshots/t06-brand-type.png、t06b-brand-H.png、t06c~t06d-brand-*.png、t07-model.png、t07b-model-ok.png、t08-form-filled.png

### 4. 新建商品-完整提交 — 部分完成（名称/编码/品牌/型号已填，底部异步下拉未完成）

- 已完成：商品名称填"AB自动化测试商品20261014"、商品编码填"ABTEST-20261014-001"（标准 textbox，`fill` 生效）；后台类目通过树形下拉选中"智能电视111"（点击选择生效）。
- 受阻点：**品牌字段（"输入品牌名称搜索"）无法通过 agent-browser 的标准输入手段写入**。依次尝试均无效：
  1. `fill @e103 "海信"` — 文本未进入
  2. `click @e103` + `keyboard type "海信"` — 未进入
  3. `click @e103` + `keyboard inserttext "海信"` — 返回 inserted:true 但框内仍为空
  4. `eval` 查找 placeholder 含"品牌"的 input — 返回空（该 placeholder 不挂在标准 input 上）
  5. `eval` 检查点击后是否出现 ant-select 下拉浮层 — 返回"无打开的下拉浮层"
- 结论：品牌选择组件的真实输入控件未能被 `@e103` 正确命中/驱动，`@e103` 可能指向组件外层包装而非内部可输入节点。因品牌为必填，完整提交无法走完。
- **这是本次测试的关键发现**（见下节"对 agent-browser 的启示"），非被测功能缺陷，也非环境问题，而是**自定义输入组件与通用自动化定位之间的适配障碍**。
- 证据：screenshots/t05b~t05d-brand-*.png（三次输入尝试品牌框均为空）

## 对 agent-browser 的启示（能力边界的具体一例）

- 标准表单元素（textbox、树形下拉选择）agent-browser 的 `fill` / `click`+语义选择工作良好（名称、编码、后台类目均顺利完成）。
- 但对**封装较深的自定义搜索选择组件**（如本例品牌框），`fill` / `keyboard type` / `keyboard inserttext` 均可能失效，因为 `@eN` 命中的是组件包装节点、而非内部真实 input。
- 这与官方文档"自定义输入组件 fill 失效时用 focus + keyboard"的提示一致，但本例进一步说明：当**连内部 input 都定位不到**时，需要更精细的 DOM 分析（找到真实可输入节点的精确选择器）或改用组件自身的交互路径（如果它是"点击弹面板选择"而非"输入搜索"）。
- 价值：这正是真实自动化会遇到的典型难点。agent-browser 的 `eval` 能力在此发挥了诊断作用——通过 `eval` 查询 DOM 确认了"placeholder 不在 input 上""无 ant-select 浮层"，把"输入失败"精确定位到"组件结构特殊"，而非盲目重试。
