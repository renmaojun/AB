# 用户故事 → 结构化用例 生成指引

本文件指导如何把一句自然语言的“用户故事 / 测试意图”转换成符合规范的结构化 Markdown 用例
（字段规范见 [case-format.md](case-format.md)）。目标是让“帮我写个用例：测 XXX”有章可循、产出一致。

## 用户故事的常见形态

用户给出的意图通常是下面几种之一：

- 场景句：“测试点击导航栏电视能进入电视页面”
- 角色-动作-结果（用户故事体）：“作为访客，我点击企业 logo，应进入海信官网”
- 功能名 + 期望：“搜索功能，输入关键词要能出结果”
- 带数据的断言：“空调大1匹页面要有价格 1763 的商品”

无论哪种，都按下面的方法抽取出 11 个字段。

## 转换步骤

### 1. 抽取“动作”和“预期”

先把故事拆成两部分：

- 动作：用户做了什么（打开/点击/输入/悬停/选择……）。
- 预期：应观察到什么结果（跳转到某页、出现某文本、某价格存在……）。

一句话里往往动作与预期混在一起，拆开它们是关键。例：
“点击导航栏电视能进入电视页面” → 动作=点击导航栏“电视”；预期=进入电视相关页面。

### 2. 推导元数据字段

| 字段 | 推导方法 |
|------|---------|
| 模块 | 动作发生的功能区域：导航栏→“导航”；搜索框→“搜索”；购物车→“购物车”；登录→“登录” |
| 功能点 | 更具体的被测点，如“顶部导航栏分类入口”“首页关键词搜索” |
| 用例标题 | 一句话复述“动作 → 预期”，可读、可判定 |
| 用例类型 | 主流程/核心入口→冒烟或功能；校验历史问题→回归；输入边界→边界；错误输入/异常路径→异常 |
| 设计技法 | 完整走一条路径→场景法；按取值划分→等价类；临界值→边界值；猜测易错点→错误推测 |
| 优先级 | 核心交易/主流程→P0；重要功能→P1；次要/外链/辅助→P2；边缘→P3 |
| 用例编号 | `TC-<模块英文缩写>-<三位序号>`，如 TC-search-001、TC-nav-003；同模块顺延序号 |
| version / last-updated | 新用例 version=1，last-updated 填当天日期 |

模块英文缩写约定：搜索=search，导航=nav，购物车=cart，登录=login，商品详情=item，结算=checkout。无合适缩写时取功能英文词。

### 3. 写前置条件与测试数据

- 前置条件：执行前必须成立的状态。默认写“目标环境可访问（基址见 _ENVIRONMENTS.md，默认 test）”；若需登录态等再补充。
- 测试数据：把故事里出现的具体值提取为键值对。
  - 起始页用相对 `起始路径`（如 `/`），不写死域名。
  - 故事里的关键词、价格、分类名、账号等都列为测试数据键，供步骤和预期代入。例：“搜索关键词: 电视”“期望商品价格: 1763”。

### 4. 拆“测试步骤”（只写意图，不写选择器）

把动作拆成有序的操作意图，每步只说“做什么”，不写 `@eN` 或 CSS。常见拆法：

- 打开页面 → “打开<页面>”“等待页面加载完成”
- 定位+操作 → “在<区域>找到<目标>并点击/输入<数据>”
- 二级菜单 → “将鼠标悬停在<一级项>上展开二级菜单”“在二级菜单中点击<二级项>”
- 提交 → “按回车提交”或“点击<提交按钮>”
- 跳转后 → “等待目标页面加载完成”；可能新开标签时加“若在新标签页打开则切换过去”

执行时由 agent 按核心循环（snapshot→选 ref→操作→re-snapshot）现场定位，步骤不绑定具体元素。

### 5. 写“预期结果”（每条可验证、可取证）

把预期拆成若干独立断言，每条都要能用 agent-browser 取到证据（URL/标题/可见文本/截图）。写法建议：

- 跳转类：“点击后页面发生跳转（URL 相对起始页变化）”，必要时限定“路径包含 X / 查询串包含 Y”。
- 内容类：“页面可见文本中出现 <关键词/价格>”“标题包含 <文本>”。
- 页面健康：“目标页面能正常拍到快照（非错误页/空白页）”。
- 跨域外链：“目标页面域名为 <目标域名>，不再是 <来源域名>”。

避免写成不可判定的主观描述（如“页面好看”“体验流畅”）。

### 6. 对不确定信息的处理（重要）

生成用例时若对站点实际情况不确定（某入口是否存在、某价格是否真实、二级项的确切文案），按以下原则：

- 照用户意图如实写入预期，不臆造“安全”的模糊预期来迁就。严格的预期即使首次执行失败，也比模糊预期有价值——失败会暴露“用例预期与站点不符”，再据实修正。
- 在用例中可保留用户给的原始措辞；执行时按站点真实文案定位（如用户写“大一匹”，站点为“大1匹”，执行时按实际点击，判定不受影响）。
- 不把运行时才知道的 `@eN`、具体 URL 结构写进用例。

## 示例：故事 → 用例

**用户故事**：“测试点击首页顶部企业 logo，跳转进入海信企业官网”

抽取：动作=点击顶部企业 logo（海信官网入口）；预期=进入海信企业官网（离开商城域名）。

生成用例骨架：

```markdown
---
用例编号: TC-nav-003
模块: 导航
功能点: 首页顶部企业 logo 外链
用例标题: 点击首页顶部企业 logo 应跳转进入海信企业官网
用例类型: 功能
设计技法: 场景法
优先级: P2
version: 1
last-updated: <当天日期>
---

## 前置条件
- 目标环境可访问（基址见 _ENVIRONMENTS.md，默认 test）

## 测试数据
- 起始路径: /
- 入口名称: 海信官网

## 测试步骤
1. 打开海信商城首页
2. 等待页面加载完成
3. 在页面顶部找到企业 logo（海信官网入口）并点击
4. 若在新标签页打开，切换到该新标签页
5. 等待目标页面加载完成

## 预期结果
- 点击后进入海信企业官网（目标页面域名为海信官网域名，不再是商城域名）
- 目标页面内容体现“海信”企业官网（标题或可见文本包含“海信”且非商城搜索/商品页）
- 目标页面能正常拍到快照（非错误页/空白页）
```

## 产出要求

- 文件名与用例编号一致，放在 `test-cases/` 下，如 `TC-nav-003.md`。
- 字段齐全，顺序与模板一致（见 `_TEMPLATE.md`）。
- 一次给多个故事时，逐个生成独立 `.md`，编号在同模块内顺延。
- 生成后向用户简述每条用例的编号/模块/优先级，并指出其中依赖站点真实数据、首次执行需核验的断言。
